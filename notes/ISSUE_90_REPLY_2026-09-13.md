## 3. The κ registry (the "k registry")

Two layers, kept apart:

- **Content.** The extension's `star-registry.ts` + `scripts/star-registry.mjs` is an adapter to the UOR Foundation's [**kappa-registry**](https://github.com/UOR-Foundation/kappa-registry) — open source (Rust, one content-addressed store behind OCI/Git/S3/Nix/ATProto interfaces), pinned upstream at `2af8656` — using its blob interface: `PUT`/`GET /v2/<namespace>/blobs/sha256:<κ>`. It is a **resolve-by-κ content store**: what goes up is a `star-registry-entry/1` (a selected Star *reading*, not the full key; canonical sorted UTF-8 JSON), what comes back is re-hashed before anything is believed, and no identity is attested there. Open infrastructure, not a product surface; no hosted instance of ours exists yet (the live-acceptance script is written, not run). So yes: a **fetch-then-re-derive** import path is exactly the right shape, and the same discipline applies to whatever you publish on hyperswarm: fetch, re-derive, and never trust a registry for content.
- **Assertions.** Where a VTA record or a Hold commitment would *register as a claim* is the identity-assertion layer of the same registry (its `IdentityAssertion` basis ladder and `assert_double_entry` bilateral mint). Our convergence notes on that are public in [`mitchuski/uor-kappa-mage`](https://github.com/mitchuski/uor-kappa-mage); nothing is built on either side there yet. OpenVTC's own registries (`did:webvh` hosting) are a third thing — identity hosting, not κ.

## 4. Dual-proof credentials: built and waiting for your assertion key

Your document-loader note was the right cut. The Star Hold verifiers (the reference runtime and agentprivacy-mcp) now:

- accept a **proof set** (`proof: [...]`), every proof checked over the unsecured document (the whole `proof` property removed), composed fail-closed: any supported proof that *fails* → `invalid` (a second proof never papers over a broken one); otherwise one supported proof that verifies → `valid`; otherwise `unavailable` if a supported proof could not be resolved; otherwise `unsupported`, naming every suite. Per-proof verdicts are returned. A single proof keeps the old shape exactly.
- reach `did:cid:<did>#key-assertion-1` two ways, both offline from the verifier's point of view: a **pinned Multikey** (your option 2) or a **caller-fetched DID document** (your option 1 — the resolver result from `GET /1.0/identifiers/<did>` passed in as-is; relative method ids like `#key-1` are normalised; Multikey and Ed25519 JWK entries are read; secp256k1 / X25519 entries are refused *with a reason*). No network call inside verification.

We tested it against the House's **live** document from `https://archon.technology/1.0/identifiers/did:cid:bagaaiera7vsj…` (versionSequence 35, `assertionMethod: ["#key-1"]`, secp256k1 only — no `#key-assertion-1` yet). So today an `eddsa-jcs-2022` proof from the House naming `#key-assertion-1` reads `unavailable` (not `invalid`), and it flips to `valid` the moment the Multikey is published — no code change on our side. Ten checks cover it (runtime 55/55, mcp suite green); the fixture uses the House's real `did:cid` with a *test* Ed25519 seed.

This also answers the credential-vs-operation question from our end: as a credential with the dual set, the acceptance item verifies natively; as a raw operation it stays a declared `unsupported` item, which is the honest state. **Ask:** when the assertion key is published and a real dual-proof credential exists, post one here (or the DID to fetch it by). We'll run it end to end and report the item's state.
